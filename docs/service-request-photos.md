# ادامه Service Request: مدیریت درخواست و تصاویر

تمام endpointهای زیر به Bearer Token معتبر و نشست فعال Identity نیاز دارند. UserId از JWT گرفته می‌شود؛ درخواست و فایل کاربر دیگر مانند رکورد ناموجود با 404 پاسخ داده می‌شوند. مسیرهای زیر نسبت به ریشه سرویس هستند؛ در سایت موجود `https://api.zumaris.com` پیشوند `/service-request` را اضافه کنید.

| متد | مسیر | کاربرد |
| --- | --- | --- |
| GET | `/api/service-requests?status=Submitted&page=1&pageSize=20` | لیست درخواست‌های کاربر، فیلتر اختیاری وضعیت، صفحه‌بندی |
| GET | `/api/service-requests/{id}` | جزئیات و تصاویر |
| PUT | `/api/service-requests/{id}` | ویرایش کامل اطلاعات قابل تغییر |
| POST | `/api/service-requests/{id}/cancel` | لغو با دلیل |
| GET | `/api/service-requests/{id}/timeline` | تاریخچه وضعیت |
| POST | `/api/service-requests/{id}/photos` | افزودن یک یا چند تصویر با multipart/form-data |
| GET | `/api/service-requests/{id}/photos/{photoId}` | دریافت فایل توسط صاحب درخواست |

POST ثبت اولیه نیز مانند قبل برقرار است. جزئیات/ویرایش/لغو خروجی `{ request: { ...fields, version }, photos: [...] }` می‌دهند. لیست شامل `items`, `totalCount`, `page`, `pageSize` است؛ pageSize بین 1 و 100 و page بین 1 و 1000000 است. نام‌های وضعیت Submitted، Assigned، InProgress، Completed و Cancelled هستند؛ فیلتر ناشناخته رد می‌شود. ترتیب لیست createdAtUtc نزولی و سپس شناسه است. تاریخچه با زمان و شناسه مرتب می‌شود و زمان‌ها UTC هستند.

## ۱. اسکریپت دیتابیس — خودتان اجرا کنید

اگر نسخه قبل را نصب کرده‌اید و migration 001 اجرا شده است، فقط این فایل را روی اسکیما **zumaris_service_request** اجرا کنید:

`database/service-request/002_request_lifecycle.sql`

فایل، CHECK محدودکننده وضعیت را در یک ALTER با وضعیت‌های کامل جایگزین می‌کند و ردیف‌های فعلی را تغییر نمی‌دهد. قابل اجرای مجدد است، مشروط به اینکه constraint اولیه با همان نام وجود داشته باشد. برای نصب تازه ابتدا 001 و سپس 002 را اجرا کنید. جدول تصاویر همان جدول metadata نسخه قبل است؛ ستون باینری اضافه نشده است.

حساب برنامه اکنون به SELECT/INSERT/UPDATE در اسکیما نیاز دارد. مجوز را DBA با نام و Host واقعی حساب تنظیم کند. **هیچ اسکریپت دیتابیسی در Codex اجرا نشده است**؛ تست SQL واقعی، رقابت قفل‌ها و rollback باید بعد از اجرای دستی روی محیط آزمایشی تأیید شوند.

## ۲. Version و قواعد وضعیت

از GET جزئیات، `request.version` را بگیرید و همراه PUT، لغو یا آپلود بفرستید. هر تغییر موفق Version را یک واحد بالا می‌برد؛ مقدار قدیمی یا وضعیت نامجاز 409 است. پس از 409 دوباره جزئیات را بخوانید و خودکار با Version حدسی Retry نکنید.

- ویرایش فقط در Submitted مجاز است. بدنه مثل POST ثبت اولیه است، به‌علاوه فیلد `version`. UserId، Status و TechnicianId قابل تغییر توسط این API نیستند.
- لغو در Submitted یا Assigned مجاز است؛ دلیل پس از Trim باید 3 تا 500 کاراکتر باشد. تغییر وضعیت و درج رویداد Cancelled در یک تراکنش است.
- افزودن عکس در Submitted یا Assigned مجاز است. تصاویر قبلی پس از لغو همچنان برای صاحب درخواست قابل دریافت‌اند.
- تخصیص تکنسین یا حرکت به Assigned/InProgress/Completed endpoint عمومی ندارد؛ این وضعیت‌ها برای اتصال workflow سرویس‌های بعدی رزرو شده‌اند. نمی‌توان آن‌ها را با PUT تعیین کرد.

بدنه نمونه لغو:

```json
{ "reason": "نیاز به سرویس برطرف شد", "version": 2 }
```

## ۳. پوشه تصاویر در سرور IIS

مقدار پیش‌فرض تنظیم **Storage:RootPath** اکنون `D:\ZumarisData\Uploads` است؛ بیرون از ریپوزیتوری و پوشه Publish. آن را متناسب با سرور در appsettings یا متغیر محیطی `Storage__RootPath` تغییر دهید. در Linux مسیر مطلق مناسب همان ماشین لازم است.

روی سرور پوشه را بسازید و به هویت Application Pool سرویس Service Request مجوز **Modify** بدهید. مثال زیر را با نام واقعی Pool خود جایگزین کنید:

```powershell
New-Item -ItemType Directory -Force -Path 'D:\ZumarisData\Uploads'
icacls 'D:\ZumarisData\Uploads' /grant 'IIS AppPool\Zumaris.ServiceRequest:(OI)(CI)M'
```

این پوشه را به Virtual Directory عمومی تبدیل نکنید؛ فایل‌ها از endpoint احرازشده خوانده می‌شوند. سرویس نام اصلی فایل را استفاده نمی‌کند و مسیر تولیدشده شبیه زیر است:

```text
service-requests/{requestId}/{randomPhotoId}.jpg
```

فقط مسیر نسبی در دیتابیس ذخیره می‌شود، نه مسیر فیزیکی سرور یا محتوای عکس. GET جزئیات، شناسه و `downloadPath` را می‌دهد؛ این مسیر نسبت به ریشه سرویس است، مثلاً:

```text
https://api.zumaris.com/service-request/ + api/service-requests/{id}/photos/{photoId}
```

برای نمایش در فرانت‌اند، فایل را با Bearer دریافت و Blob/Object URL بسازید؛ توکن را داخل query string یا URL عکس قرار ندهید. پاسخ دانلود دارای no-store و nosniff است.

## ۴. آپلود از Swagger

1. در Identity لاگین و Access Token را کپی کنید.
2. در Gateway، **Service Request Service** را انتخاب و در Authorize توکن را وارد کنید.
3. GET جزئیات درخواست را بزنید و Version را بخوانید.
4. endpoint `POST .../{id}/photos` را باز کنید؛ `Version` و فایل‌های فیلد **Photos** را انتخاب و Execute کنید.
5. پاسخ شامل شناسه‌ها و Version جدید است؛ با GET جزئیات یا مسیر دانلود فایل را بررسی کنید.

فرمت‌های پذیرفته‌شده JPEG و PNG هستند. هر فایل حداکثر **5 MiB**، هر درخواست مجموعاً **8 تصویر**، حداکثر 12 مگاپیکسل و حداکثر 10000 پیکسل در هر بُعد است. محتوا Decode می‌شود؛ نام/پسوند/MIME ارسالی تعیین‌کننده نیست. خروجی دوباره با فرمت شناسایی‌شده نوشته و metadata با Strip حذف می‌شود؛ برای ورودی چندفریمی فقط فریم اول ذخیره می‌شود. رمزگذاری/پردازش تصویر با Magick.NET-Q8 انجام می‌شود؛ فایل‌های native همراه خروجی Publish لازم‌اند و نباید از پوشه خروجی حذف شوند.

در هر بار آپلود 1 تا 8 فایل بفرستید؛ سقف 8 روی مجموع قبلی و جدید اعمال می‌شود. ثبت metadata دسته‌ای اتمیک است و قفل ردیف درخواست/slot یکتا مانع عبور دو آپلود هم‌زمان از سقف می‌شود. هم‌زمان چند آپلود برای یک Version نفرستید؛ یکی می‌تواند 409 بگیرد.

فایل‌ها ابتدا با نام موقت در همان پوشه نوشته و سپس به نام نهایی منتقل می‌شوند. اگر فایل بعدی نامعتبر باشد، یا دیتابیس قبل از Commit به‌طور قطعی Version/وضعیت/سقف را رد کند، فایل‌های همان دسته حذف می‌شوند. در خطای نامشخص Commit، فایل‌ها عمداً باقی می‌مانند تا metadata احتمالیِ Commit‌شده به فایل حذف‌شده اشاره نکند. پس از قطعی یا crash، فایل‌های قدیمی بی‌مرجع یا `.tmp` را با metadata تطبیق دهید؛ فایل‌های فعال یا دسته‌های در حال پردازش را حذف نکنید. پاک‌سازی خودکار زمان‌بندی نشده است. پوشه آپلود و دیتابیس باید با هم بکاپ‌گیری شوند.

## ۵. انتشار و محدودیت بدنه

ServiceRequest.Api و Gateway را هر دو با IISProduction دوباره Publish کنید. دامنه عمومی، SSL و پورت 443 تغییر نمی‌کنند؛ مقصد داخلی Service Request همان 5002 است. web.config هر دو برنامه سقف IIS را 44 MiB قرار می‌دهد و Gateway برای Kestrel/IIS هم همین سقف را دارد. endpoint آپلود حد multipart را 42 MiB قرار می‌دهد تا 8 فایل 5 MiB با سربار فرم قابل ارسال باشد. محدودیت پایین‌تر reverse proxy یا تنظیم سراسری IIS می‌تواند زودتر 413 یا 404.13 برگرداند.

ASP.NET ممکن است فرم‌های بزرگ را در پوشه موقت buffer کند؛ هویت Pool باید به پوشه موقت برنامه هم دسترسی نوشتن داشته باشد. در صورت نیاز `ASPNETCORE_TEMP` را به یک پوشه خصوصیِ قابل‌نوشتن در سرور تنظیم کنید. نصب تازه همچنان به .NET 8 Hosting Bundle نیاز دارد.

تست‌های HTTP با دیتابیس حافظه‌ای و فایل‌های واقعی در پوشه موقت اجرا شده‌اند: مالکیت، Version، وضعیت، سقف مجموع عکس‌ها، هم‌زمانی، جبران فایل در خطا، decode واقعی JPEG/PNG، مسیر traversal و Swagger. Release و web.config در Codex بررسی می‌شوند؛ اجرای Windows IIS و SQL سرور شما جداگانه باید تأیید شوند. بررسی وجود/مالکیت Property و معتبر بودن شناسه‌های دسته/ناحیه همچنان به اتصال سرویس‌های مرجع وابسته است.
